## 7. 风险与回滚

最紧的一条：把 `v0.3.0` 读成对外教学服务已经可以开放。G3 仍因 #47 未通过而不能发布。标签说明必须写「不是对外发布」。

热修更可能落在这些路径：

- 第二次 retire。V009 已在 main。若审计 `target_id` 又指错行，热修只改 retire 的 RETURNING 路径，不改发布路由。
- 资产元数据路由把合成 `file_id` 当成已经存了字节。热修是收紧文档或拒绝缺少存储批次的调用，不在热修里选介质。
- 演练脚本连错库。热修是收紧库名检查。已经写进 `k12` 的演练行要人工确认后再删。

回滚应用代码：对 Final 提交做反向提交，经 PR 合入，再打 `v0.3.1`。不删除远程 `v0.3.0`，不移动 `v0.2.0`。数据库不要为了回到旧代码去执行 V009 的 down：down 在同一绑定已有两条相同 status 时会 RAISE，这是有意的。旧代码也依赖已经不存在的三列 UNIQUE 才能拒绝第二次 retire。

延后项若在服务已经能被老师的浏览器访问时仍不做，会踩到这些情况：

- #31 的无长度头半边：客户端不送 `Content-Length` 时，1 MiB 检查不生效，大正文可以进入进程。本机合成 HTTP 还没有这批外部客户端。
- #32 的其余路由：登录和 `/health/ready` 以外没有每分钟窗。登录本身仍有 5 次 / 15 分钟和 IP 20 次 / 分钟。
- 不打 0.3.0、也不做 #2 / #3：没有新的生产故障，但 M-10 / M-11 继续没有合格证据，下一次若有人把 main 说成可试用，仍然缺少那两页记录。
