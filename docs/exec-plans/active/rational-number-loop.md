对应：第一段代码只做网页上的核验、出卷和确认，覆盖 US-01、US-02 和确认这一步（US-04 里不依赖拍照的部分）。安卓拍照、上传和 AC-06 排在这段之后。桌面壳更后面。试用门槛仍是网页和安卓都能走完，那不是第一段的完成线。

骨架在合成数据上已经能做到：

| --- | --- | --- |
| 未核准拒绝 | 题目或答案未核准时拒绝出卷，不写学生卷 | `test_unapproved_issue_is_refused_and_writes_nothing` |

## 要证明的事

在浏览器里，老师可以核验并发布一道题，给一名学生生成一份卷，打开 PDF，并确认一条作答记录。服务端拒绝未核准题目的正式出卷。相同确认再提交一次不产生第二条记录。这一段不包含手机拍照。

本地开发使用合成题目、合成学生和假适配器。这不代替真实学生试用前的运行时安全验证，也不代替数据库和文件在同一恢复点的联合恢复。

## M1 契约

下面四项是这一段的执行契约。服务端和网页技术栈已由 ADR 0012 采纳，框架包还没安装。机构还没确认的地方标为待确认。预期结果是做出来之后必须能观察到的事。

### 发卷时冻结什么

冻结的是这一次发卷用到的：题目版本、适用答案版本、素材标识、版面。素材标识包括原图和题目图的文件标识。版面包括题序、页码、学号的位置和模板标识。卷面不印姓名。

旧 PDF 用发卷时写下的文件标识取回，不按后来的题库重新渲染。标识还在、字节却变了，就视为取回失败，并留下原来的标识。

可观察到：改题库之后，旧卷上的版本标识和文件标识不变；用旧标识读到的字节仍是发卷时那一份。

待确认：PDF 由哪个程序渲染。ADR 0012 没有选定渲染程序。

### 确认的操作键

操作键的范围是这一次确认：学生卷、小问、老师。复核版本不放进键里，另外核对。版本变了就拒绝，即使操作键是新的。

| 情况 | 结果 |
| --- | --- |
| 同一操作键，内容相同 | 返回原来的确认记录，不写第二条 |
| 同一操作键，内容不同 | 拒绝 |
| 两个不同的键同时确认同一小问的同一复核版本 | 一个成功。另一个得到冲突，并提示重新查看。不静默覆盖 |
| 复核版本已经变了 | 拒绝 |

待确认：操作键的具体字符串由谁生成。方案 1.1 第 10.2 节只把它写成输入，没有定格式。

### 没有上传时的待确认作答

这一段不拍照、不上传。合成夹具提供一条已经绑在该学生卷和小问上的待确认作答。内容是合成文本，或一个标明为夹具的页标识。里面没有真实学号、姓名或学生照片。

建议若要出现，只来自假适配器的固定输出，并且输出标明是假的。不调用真实模型。

可观察到：老师确认这条夹具之后，出现一条正式记录。相同操作键再提交一次，正式记录仍是一条。

### 四个端口各管什么

| 端口 | 负责 | 不负责 |
| --- | --- | --- |
| catalog | 题目版本和适用答案版本是否都已核准，以及发布记录里的版本标识和素材标识 | 不保存学生卷，不写出卷结论 |
| practice | 学生卷、发卷时冻结的引用、确认记录、操作键的重放和冲突。未核准时拒绝正式出卷 | 不改题目正文 |
| PDF 渲染 | 按已冻结的版本和版面生成字节，并返回文件标识。失败时卷留在待渲染 | 不决定能否出卷。渲染程序待确认 |
| 授权 | 这一次请求的老师是否可以处理这个学生和这门学科。拒绝时 practice 不写卷，也不写确认 | M1 用内存假规则。真实分工等 DEC-02，待确认 |

## 不要做

- 不建知识卡、PPT、家长报告、iOS、桌面安装包、安卓工程。
- 不一次建满六个切片目录。第一段只有 `catalog` 和 `practice`。允许名单是 `PHASE_SLICES`，默认仍是这两项。授权先做 practice 用的内存端口。`knowledge`、`identity`、`analysis`、`delivery` 等有代码再创建，并在同一次改动里放宽配置。
- 不接真实模型，除非机构已经确认 DEC-03。未确认时只用假适配器，并且输出标明是假的。
- 不把假适配器的演示写成 AC-04 或 AC-09 已通过。
- 不在界面里判断能否出卷或能否确认。
- 不新增第二套业务规则。

## 步骤

1. 选定本切片的语言和工程文件。若选定，先写新的 ADR 取代 ADR 0010 里的对应句子，并补上锁文件。未选定时停在这一步问用户，不并行开两套框架。
2. 先提交端口和公开 `api` 的数据类型：核准快照、创建卷、确认作答。只含普通数据：标识、版本、错误码。不含网页对象和数据库行。上传页留到安卓那一段。
3. 只在 `catalog` 和 `practice` 实现 R1、R2、R3、R5 的最小规则。授权用 practice 里的内存端口，不先建 `identity` 目录。
4. core 测试用假端口。至少覆盖：未核准出卷被拒绝；确认后正式记录出现；相同操作键重放返回原结果；不同内容的同一操作键被拒绝。
5. 组合根 `backend/bootstrap/compose.py` 只做装配。日志适配器写标准输出 JSON。故意制造一次确认失败，用 request_id 在输出里找到 ERROR。
6. 一条命令能把这个用例跑起来。把 `scripts/check.conf` 的 `SERVICE_CMD` 设成那条启动命令，把 `BUSINESS_TEST_CMD` 设成最小业务冒烟，并写进 README。文档冒烟可以留下。`TEST_KIND` 保持 `docs`，直到 `TEST_CMD` 本身就是 core 测试。现在 `APP_DIRS=.`，仓库里没有 Web 或 Python 依赖清单，M-09 因此是 N/A。第一次加入清单时，同一改动里把 `APP_DIRS` 写成清单所在目录，并把 `INSTALL_CMD` 写成锁定安装命令。
7. 网页在老师这台电脑的浏览器里能核验、能打开 PDF。到这里第一段结束。
8. 下一段再做安卓拍照、上传和缺页。网页和安卓都走完之前，不宣称 AC-06 通过。
9. 桌面壳排在网页已经顺畅之后。第一段不安装 Tauri 或 Electron。

## 完成时要看到

- 测试命令的退出码是 0，输出在 `docs/evidence/`。文档冒烟单独标成 DOCS，不写成 core 单测已通过。
- 门禁表 G1。这一段适用的 MUST 有 FAIL 就不能说完成。若这段还没有持久化，不把尚未存在的数据库联合恢复写成失败来挡住完成；写了持久化就要有可回退的迁移和该阶段的恢复证据。
- 新边界有日志。日志里没有姓名、学号、密钥和整段请求体。
- 上面四项契约的预期结果都有一次可重复的观察。
