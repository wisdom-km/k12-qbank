# 执行计划：有理数运算一条闭环

状态：计划。还没有业务实现。2026-11-14。
对应：PRD 的 US-01 到 US-04，验收 AC-01 到 AC-04 的最小厚度。US-06 的真机留在本计划的最后一步，不在第一步假装完成。

本计划自包含。不依赖某次聊天。

## 现状

仓库有约束文档、kernel 里的日志端口和 Result、以及门禁脚本。没有题目、没有数据库、没有网页、没有安卓工程。技术栈是提议。

## 要证明的事

服务端可以：拒绝未核准题目的正式出卷；给一名学生冻结一份卷；接收一页；保存一条建议；在老师确认后留下正式记录；相同操作再提交一次不产生第二条确认。

## 不要做

- 不建知识卡、PPT、家长报告、iOS。
- 不接真实模型，除非机构已经确认 DEC-03。未确认时只用假适配器，并且输出标明是假的。
- 不把假适配器的演示写成 AC-04 或 AC-09 已通过。
- 不在界面里判断能否出卷或能否确认。
- 不新增第二套业务规则。

## 步骤

1. 选定本切片的语言和工程文件。若选定，先写新的 ADR 取代 ADR 0010 里的对应句子，并补上锁文件。未选定时停在这一步问用户，不并行开两套框架。
2. 先提交端口和公开 `api` 的数据类型：核准快照、创建卷、上传页、确认作答。只含普通数据：标识、版本、错误码。不含网页对象和数据库行。
3. 在 practice 和 catalog 实现 R1、R2、R3、R5 的最小规则。identity 先用一个固定的「允许 / 拒绝」端口，内存实现即可。
4. core 测试用假端口。至少覆盖：未核准出卷被拒绝；确认后正式记录出现；相同操作键重放返回原结果；不同内容的同一操作键被拒绝。
5. 组合根 `backend/bootstrap/compose.py` 只做装配。日志适配器写标准输出 JSON。故意制造一次确认失败，用 request_id 在输出里找到 ERROR。
6. 一条命令能把这个用例跑起来。把 `scripts/check.conf` 的 `RUN_CMD` 改成那条命令，并写进 README。文档冒烟可以留下，但不能代替这个用例的测试。
7. 真机、真实 PDF 和真实模型放到 M3。那之前不宣称 AC-06 通过。

## 完成时要看到

- 测试命令的退出码是 0，输出在 `docs/evidence/`。
- 门禁表 G1。任一 MUST 为 FAIL 就不能说完成。
- 新边界有日志。日志里没有姓名、学号、密钥和整段请求体。

## 是否影响规格

若实现时发现 R1 到 R6 必须放宽，先改 PRD 和 ARCHITECTURE，再改代码。不要只改代码。
