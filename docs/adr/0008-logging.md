# ADR 0008 结构化日志和请求 ID

## 背景

测试或试用时一次操作失败，要能从一条请求 ID 找到是哪一层、什么原因。现在就定，不等出了事故再补。

## 选项

1. 在领域代码里直接 `print` 或使用具体日志库。
2. 领域和应用只依赖 kernel 里的 Logger 端口。具体格式在适配器和组合根配置。日志写到标准输出。

## 决定

选 2。一条日志是一个事件，字段固定：

| 字段 | 含义 |
| --- | --- |
| time | 事件时间，UTC，ISO-8601 |
| level | ERROR、WARN、INFO、DEBUG |
| event | 稳定的事件名 |
| request_id | 这一次操作的标识 |
| module | 切片或适配器名 |
| outcome | 结果或错误码 |
| duration_ms | 这一步耗时 |

级别：ERROR 是操作失败。WARN 是没失败但不正常，例如重试、降级、拒绝访问。INFO 是该留下的业务事件。DEBUG 是诊断细节，默认关。

请求 ID 在 HTTP 入口或后台任务入口生成。若调用方传入的标识不符合安全字符规则，就丢弃并自己生成。它作为参数传入用例和适配器，不用进程内全局变量。

绝不记录：密码、token、API key、session、连接串、密钥、银行卡、学生姓名、学号、整页照片、整段请求体、完整提示词。外部文本写入日志前去掉换行。

去向：进程写标准输出，由运行环境收集。本地开发在终端看。保留多久、谁可以看，等 DEC-03。在此之前默认只有开发者和机构指定的运行负责人能看，老师不靠原始日志教学。指标和链路追踪未落地。

## 后果

core 测试可以用内存 Logger 断言某次失败产生了带 request_id 的事件。机器检查见 `scripts/check_logging.py`。它查文档字段，并拒绝 kernel、domain、application 里的 `print` 和具体日志库 import。它查不到所有绕过写法，所以 review 仍要看新增边界有没有日志。

## 状态

采纳。2026-11-14。保留期限待定标。
