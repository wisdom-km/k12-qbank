# ADR 0017 草稿形状用 JSON Schema 校验

## 背景

题目草稿和答案草稿的字段写在 ADR 0013 和 ADR 0014。两边各有一套手写解析。核对页负责生成，题库负责读入。字段一增加，两套代码可能只改一边。

题库已经锁定依赖，不为此新增包。核对页也没有第三方依赖。领域不能导入 FastAPI 或 Pydantic。

## 选项

1. 用 Pydantic 模型作为两边的契约。题库里已有这个包，核对页要新加，领域也会依赖框架。
2. 把 JSON Schema 放进 catalog。题库解析前用标准库检查。核对页复制这两份文件，写入前用同一套关键字检查。不新增包，不把两个仓库合成一个。

## 决定

选 2。

- 正式文件是 `backend/catalog/contracts/` 里的 `k12-question-draft.v1.schema.json` 和 `k12-answer-draft.v1.schema.json`。不放在 `backend/` 的新目录下，因为门禁只允许已知切片。
- 题库的 `parse_question_draft` 和 `parse_answer_draft` 先做形状检查。失败仍是 `not_draft`，说明里带字段路径。通过之后才做原来的语义检查。语义没变：草稿仍不能发布，一个选项的选择题仍按 ADR 0013 的已知差距处理。
- 领域只读随包发布的契约文件，不读用户目录，不读数据库。
- 核对页的 core 不读文件。网页层读取复制来的契约，把字典交给 core。写入和预览前检查。失败错误码是 `CONTRACT`，这一次不写文件。
- 校验器只实现这些文件用到的关键字。文件里出现别的关键字时，检查失败，而不是跳过。
- 不新增依赖。PostgreSQL 仍不连接。

## 后果

改字段时同时改题库的契约文件、核对页的复制件、两边的测试。语义规则仍在解析器里，不全部搬进 Schema。

## 状态

采纳。2026-11-17。不取代 ADR 0013 或 ADR 0014。补上机器可执行的形状检查。
